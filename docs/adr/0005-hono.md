# 0005 · Hono as the HTTP Framework

- Status: Accepted
- Date: 2026-10-01
- Related: [design/07](../design/07-http-api.md)

## Context

The panel needs an HTTP framework for the REST API, static assets, and middleware (authentication, RBAC, audit, CSRF, rate limiting). Requirements: lightweight, good TypeScript types, works with zod, easy end-to-end types for the frontend.

## Decision

Use Hono on `@hono/node-server`, with `@hono/zod-validator` for validation and Hono's `hc` client for frontend types. WebSockets bypass Hono and are handled directly on the Node HTTP server's `upgrade` event with `ws`, for full control over the handshake and backpressure.

## Options considered

| Option | Pros | Cons |
|---|---|---|
| Hono (chosen) | Very small; Web-standard Request/Response; `hc` gives end-to-end types; simple middleware model | Runs on Node through an adapter, raw throughput slightly below Fastify (irrelevant at panel load) |
| Fastify | Mature, fastest on Node, rich plugin ecosystem | Type inference less direct than Hono; plugin encapsulation has a learning curve |
| Express | Everyone knows it | Dated; weak types; async error handling needs extra work |
| tRPC | Excellent end-to-end types | Not REST; poor fit for a general HTTP API used with API tokens |

## Consequences

- Positive: route definitions are the types; frontend calls are fully typed.
- Negative: large uploads and downloads must use Node streams directly, bypassing Hono's Request abstraction (`@hono/node-server` exposes the raw `IncomingMessage`).
- Revisit when: Hono's stream handling on Node becomes a bottleneck. The few affected routes (upload, download) can be mounted on raw HTTP handlers without replacing the framework.
