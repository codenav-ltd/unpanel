# Module · PM2

> Status: Draft · Agent module: `pm2` · Capability: `pm2` · External details: [kb/pm2.md](../kb/pm2.md)

## 1. Why this is tricky

PM2 is not a system service but a **per-user daemon**. Its state lives in `PM2_HOME` (default `~/.pm2`), and the `pm2` command is usually installed in the user's own Node setup (nvm, fnm, volta), visible only on the login shell's PATH. The agent runs as root, so calling it naively goes wrong:

- `pm2` run as `root` only sees root's own PM2;
- Running as root with `PM2_HOME=/home/deploy/.pm2` **starts a new daemon as root inside the user's home if none is running**, turning file ownership to root and creating a serious mess;
- Connecting to the daemon through the Node API with a bundled pm2 version that differs from the user's daemon causes errors such as "In-memory PM2 is out-of-date".

## 2. Design

### 2.1 Discovering PM2 instances (homes)

At detection time and every 5 minutes afterwards:

1. Candidates: `/root/.pm2`, `/home/*/.pm2`, plus any `pm2.homes` configured in `agent.toml`;
2. Read `<home>/pm2.pid`, check the process is alive, and confirm `/proc/<pid>/cmdline` contains `PM2`;
3. The daemon's owner uid is the home's user;
4. Locate the `pm2` executable: first check whether the `bin` directory of `/proc/<pid>/exe` (the Node binary) contains `pm2` (nvm/fnm install both side by side); then `/usr/local/bin/pm2`, `/usr/bin/pm2`; the user can also set it manually in node settings;
5. Report the capability: `{name:"pm2", meta:{homes:[{user, home, pm2Bin, nodeBin, version, running}]}}`.

Homes whose daemon is not running are listed too (marked "not running"), but **no operation ever starts the daemon** unless the user explicitly clicks "Start PM2 daemon".

### 2.2 How commands run

Every PM2 operation runs **as the home's owner**, using **the user's own** pm2 CLI:

```
runuser -u <user> -- env -i HOME=<userHome> PM2_HOME=<home> PATH=<nodeBinDir>:/usr/local/bin:/usr/bin:/bin \
  <pm2Bin> <args...>
```

- Reads: `pm2 jlist` → JSON (the output may contain warning lines; the parser takes the first line starting with `[`);
- Before each call, check the daemon is alive; otherwise return `E_PRECONDITION("PM2 daemon is not running")`;
- Calls have a timeout (default 15 s).

The `pm2` npm package is not a dependency, which eliminates version mismatches entirely.

### 2.3 Methods

| Method | Risk | Notes |
|---|---|---|
| `pm2.homes` | read | Discovered instances |
| `pm2.list` | read | Processes of a home: name, id, mode (fork/cluster), instances, status, CPU, memory, restarts, uptime, script, cwd, Node version, log paths |
| `pm2.describe` | read | Single process details (env masked) |
| `pm2.action` | write | `start`/`stop`/`restart`/`reload`/`delete`/`reset` (by name or id) |
| `pm2.flush` | write | Clear logs |
| `pm2.save` | write | `pm2 save` (persist the process list for startup) |
| `pm2.start` | danger | Start from an ecosystem file path, or from a form (script, args, cwd, name, instances, interpreter, env) |
| `pm2.daemon.start` | danger | Start the daemon as that user (`pm2 ping`) |
| `pm2.startup.status` | read | Whether `pm2-<user>.service` exists and is enabled |
| `pm2.logs` | read (stream) | See §2.4 |

`pm2.start` can run any script, which is equivalent to running arbitrary commands as that user, hence `danger`.

### 2.4 Logs

`pm2 logs` is not used (it keeps a Node process running). The agent reads the files from `pm2_env.pm_out_log_path` / `pm_err_log_path` directly: last N lines first, then in `follow` mode `fs.watch` plus offset reads, handling rotation (inode change or the file shrinking).

### 2.5 Events (for alerting, cheap)

The agent tails `<home>/pm2.log` (the daemon's own log) and parses lines such as:

```
2026-10-01T12:00:00: PM2 log: App [api:0] exited with code [1] via signal [SIGINT]
2026-10-01T12:00:00: PM2 log: App [api:0] starting in -fork mode-
2026-10-01T12:00:00: PM2 log: App [api:0] online
2026-10-01T12:00:00: PM2 log: Script /srv/api/index.js had too many unstable restarts (16). Stopped. "errored"
```

These become `pm2.event {home, name, pmId, event: "exit"|"restart"|"online"|"errored", code?, signal?}`. The log format can change between PM2 versions, so the parser is tolerant: unrecognized lines are ignored, and a `jlist` reconciliation every 5 minutes compares `restart_time` and `status` to catch missed events.

### 2.6 cgroup caveat

If a user runs `pm2 start` in the panel terminal, the daemon inherits the terminal's cgroup. Terminals already live in the separate `unpanel-term.slice` (see [design/09](../design/09-deployment.md) §3.3), so agent upgrades do not kill PM2. `pm2.daemon.start` likewise launches through `systemd-run --scope --slice=unpanel-user.slice`. The best practice is still the systemd service generated by `pm2 startup`; the UI flags homes without startup configured.

## 3. UI

- Process table grouped by home (user): status dot, CPU, memory, restarts (highlighted when frequent), uptime, actions.
- Process drawer: details, logs (stdout/stderr toggle), environment (masked).
- Home card: PM2 version, Node version, daemon state, startup state, "Save process list" button.
